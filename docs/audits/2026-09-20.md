## Spec-corpus audit (`specs-auditor`)

**3 findings**

### Structural

**1. Two Helm release-configuration requirements are misplaced in `quality/merge-governance` — its Purpose never
describes them.** `openspec/specs/showcase/quality/merge-governance/spec.md:283`
(`### Requirement: Helm release namespaces are declared in the build`) and `:303`
(`### Requirement: Each Helm release target declares its kube context`). The spec's Purpose describes how changes land
on `main` (branch-protection rulesets and CI gates); these two requirements describe `build.gradle.kts` Helm-release
configuration (per-release `namespace`/`createNamespace` and the `releaseTargets` block resolving
`helm.local.kubeContext`), verified in the root `build.gradle.kts`. That is deployment-surface behavior, not merge/CI
governance, and it is not described by the Purpose.

**Recommendation:** move both requirements out of `merge-governance` into `deployment/helm-chart`, widening that spec's
Purpose to add "and the Gradle Helm release-target configuration (release namespaces and per-target kube contexts)";
delete both from `merge-governance`, whose Purpose is unchanged.

### Duplicate

**2. Within-spec accretion split in `deployment/helm-chart`: a "core" requirement and a matching "details" requirement
for the same subject.** `openspec/specs/showcase/deployment/helm-chart/spec.md` — "Horizontal and vertical autoscaling"
(`:161`) vs "Horizontal autoscaling details" (`:482`) + "Vertical autoscaling details" (`:497`); and "Pod disruption
budgets" (`:151`) vs "Pod disruption budget details" (`:507`). The behaviors are distinct-but-overlapping refinements
added as new requirements instead of folded into the existing ones. Flagged for judgment: candidate merges, not
automatically wrong.

**Recommendation:** merge each "details" requirement into its core requirement, carrying every scenario from the details
requirements so no behavior is lost.

**3. Legitimately shared headers across command-client / query-client and identifier / resilience4j — distinct
behaviors, no action.** `Business error translation`, `Retry of retryable failures`, `Time limiter`,
`Circuit breaker isolation of business errors`, `Automatic resilience configuration`, and `Module dependency exposure`.
Bodies are capability-specific, so each reuse is legitimate, not a merge candidate.

### Dead reference

None found. All named symbols, config keys, tasks, subagent names, and ADR references resolve. All requirement bodies
use SHALL (no `MUST`), and every requirement has at least one WHEN/THEN scenario (verified programmatically).

### Low-severity convention note (judgment call, not a hard defect)

Five requirement headers are full declarative sentences rather than noun phrases — `deployment/web-ui/spec.md:11`,
`:59`, `:75` and `identifier-extension/spec.md:44`, `:60`. If the noun-phrase convention is to be tightened, rewrite to
noun phrases. These are not bare verb phrases or fragments, so they were not counted as findings.

### Findings

**F1 — Dead cross-reference: the `org.axonframework` major suppression points at a spec section that does not exist.**
`config/dependency-updates/major-disabled.properties:4-5` points at `showcase/quality/dependency-management`, but that
spec carries no requirement covering the Axon 4.x pin (its only "Axon" mention explains _JGroups_ through Axon's

**F2 — ADR-0005's Consequences names the command-service follow-on as still pending; it has landed.**

same pattern when tested." The command service has adopted the seam (`ShowcaseCommandApplication.java:102` declares
`interface ApplicationExitHandler`, routing `flywayMigrationStrategy` through the injected `exitHandler`), exercised by
`ShowcaseCommandApplicationExitAfterFlywayMigrationIT.java` — the follow-on is done (archived change
`improve-command-service-integration-tests`). The Consequences sentence now understates reality.

**Correction:** update ADR-0005's Consequences to state the command service adopted the seam.
