### Findings

#### Structural

**`.opencode/commands/audit-agents.md:18`** — step 4 lists artifacts outside the `agents-auditor`'s fix scope as files
"the audit edited".

The step reads: `run ./gradlew spotlessApply for the formatter-wrapped files (AGENTS.md, README.md, the specs/change
dirs, and the project-authored .opencode/ markdown the audit edited)`.

This is copy-paste drift from the sibling `audit-architecture.md` (which does edit `docs/adr/`) and `audit-readme.md`
(which edits `README.md`). The `agents-auditor` definition (`.opencode/agent/agents-auditor.md:20-34`) fixes only
`AGENTS.md` and the project-authored `.opencode/` files; its README copy is routed to the docs sweep and its spec-side
copy to the corpus owner (the "Justify a new auditor" bullet in `AGENTS.md`). So `README.md` and `the specs/change dirs`
are not files this audit ever edits. Harmless (spotlessApply is a no-op on untouched files), but inaccurate — and it is
the exact kind of cross-artifact scope drift the audit exists to flag. Verified against both files.

Suggested rewrite of step 4: `run ./gradlew spotlessApply for the formatter-wrapped files the audit edited (AGENTS.md
and the project-authored .opencode/ markdown), then re-run the review-quick subagent over the resulting diff before
reporting the audit done.`

## 3. Architecture audit (architecture-auditor)

**Verdict: 2 findings, 4 advisory**

### Findings

1. **ADR-0009 under-enumerates the `axon-server-connector` exclusion — the Decision names only the gateway and the
   command service, but the exclusion is repo-wide.** Location: `docs/adr/0009-jgroups-distributed-command-bus.md:23`
   ("`axon-server-connector` is excluded from both the gateway and the command service") and `:15` ("Both the gateway
   and the command service therefore **exclude** `axon-server-connector`"). Evidence: the `exclude(group =
   libs.axon.serverConnector…, module = libs.axon.serverConnector…)` declaration appears in six build files, not two —
   all four services (`showcase-api-gateway/build.gradle.kts:19`, `showcase-command-service/build.gradle.kts:18`,
   `showcase-projection-service/build.gradle.kts:19`, `showcase-query-service/build.gradle.kts:20`) and the two clients'
   `componentTest` suites (`showcase-command-client/build.gradle.kts:41`, `showcase-query-client/build.gradle.kts:45`).
   The projection and query services use no JGroups at all; they exclude the connector because `axon-spring-boot-starter`
   pulls it in transitively and the project runs no Axon Server anywhere. Correction: amend ADR-0009's Context and
   Decision to state the invariant at its true scope — "every module depending on `axon-spring-boot-starter` (the four
   services, plus the two clients' test suites) excludes `axon-server-connector`, because the project runs no Axon
   Server." This is already parked as an owner question in `docs/ideas.md` (2026-09-14); the ADR text is the thing that
   still reads wrong.

2. **Dead rationale pointer: the Axon major-blocking entry points at a spec that carries no Axon requirement.**
   Location: `config/dependency-updates/major-disabled.properties:4` ("# Axon major blocked: framework pinned to 4.x —
   see showcase/quality/dependency-management"). Evidence:
   `openspec/specs/showcase/quality/dependency-management/spec.md` records suppression requirements for JGroups, Flyway,
   spring-data-opensearch, and springdoc only — a grep for `axon`/`Axon`/`org.axonframework` returns only the JGroups
   rationale (`:87`, which mentions Axon's JGroups extension pinning JGroups 4.x), nothing about the Axon framework's own
   major pin. The `org.springframework` entry correctly points at ADR-0004, which exists; the Axon entry points at a
   requirement that does not. Correction: add a `Requirement: Axon framework major updates are suppressed` block to the
   dependency-management spec recording the rationale (see advisory item 1 for the question the block must answer), or
   repoint the comment at the actual record.

### Advisory

1. **Why is Axon Framework pinned to 4.x** (`config/dependency-updates/major-disabled.properties:5`,
   `org.axonframework`)? The repo vendors the `axon4to5-*` migration skills and pins `axon-bom` at 4.13.3, so migrating
   to AxonIQ Framework 5 is clearly a contemplated direction — but no ADR, spec, or `AGENTS.md` sentence records why the
   project stays on 4.x rather than migrating now. This is the rationale the dead pointer in Finding 2 should point at;
   it is an open owner question, not a gap to write down as "unrecorded" (per the retrospective-ADR rule, ask before
   recording a missing _why_).

2. **Why are the OpenSearch high-level REST clients excluded in favour of `opensearch-java`?** The
   `exclude(group = libs.opensearch.client.restHighLevel…)` declaration appears in `showcase-projection-model/
   build.gradle.kts:13`, `showcase-projection-service/build.gradle.kts:29`, `showcase-query-service/build.gradle.kts:27`,
   and `showcase-query-client/build.gradle.kts:51`, while the `platform` BOM still constrains
   `opensearch-rest-high-level-client` (`platform/build.gradle.kts:54`). No ADR, spec, or `AGENTS.md` sentence records
   why the transport client replaces the high-level client in these modules — distinct from the parked low-level
   `RestClientBuilder` deprecation idea.

3. **Why are the command/event/query/DTO value types Lombok classes rather than records?** Fourteen
   `@SuppressWarnings("ClassCanBeRecord")` annotations across production code encode the choice — `showcase-command-api`
   (8: `RemoveShowcaseCommand`, `ShowcaseFinishedEvent`, `ShowcaseStartedEvent`, `StartShowcaseCommand`,
   `ShowcaseScheduledEvent`, `ScheduleShowcaseCommand`, `ShowcaseRemovedEvent`, `FinishShowcaseCommand`),
   `showcase-query-api` (2: `Showcase`, `FetchShowcaseByIdQuery`), `showcase-query-proto` (1: `QueryMessageRequestMapper`),
   and `showcase-api-gateway` (3: `ScheduleShowcaseRequest`, `ScheduleShowcaseResponse`, `ShowcaseEventDto`). `AGENTS.md`
   records the Lombok convention and the `CodeBlock2Expr` suppression convention, but never why records are rejected for
   these types. Question: is this a deliberate Jackson/Axon serialization constraint (records deserialize differently),
   or convention inertia?

4. **Is `@SuppressWarnings("FutureReturnValueIgnored")` on `ShowcaseRestController`'s list/by-id paths a deliberate
   fire-and-forget cache write, or a latent bug?** Location:
   `showcase-api-gateway/src/main/java/showcase/api/rest/ShowcaseRestController.java:183` and `:235`. The suppressed
   statements are `fetchShowcaseByIdCache.put(…, completedFuture(showcase))` and `fetchShowcaseListCache.put(query,
   completedFuture(…))` — `CompletableFuture` returns whose values are ignored. No `AGENTS.md`/ADR/spec sentence records
   that the ignored-return cache write is intentional rather than an oversight; if intentional, the suppression is the
   only trace of the choice.

Collapsed (rationale already recorded — no action needed): Jackson 2 retention (ADR-0003), Spring Boot 4 deferral
(ADR-0004), the JGroups/Flyway/spring-data-opensearch/springdoc major suppressions
(`showcase/quality/dependency-management` spec), Snyk staying out of `check` (ADR-0006), the deprecated OpenSearch
low-level `RestClientBuilderCustomizer` (`docs/ideas.md`, 2026-09-07), and the `query-api → command-api` re-export
direction (ADR-0010 sanctions it). The spec-corpus role-group decomposition, the service boundaries, and the module
dependency graph otherwise match the recorded intent; all ADR `Status` values are current and every `ADR-NNNN`
reference resolves.
