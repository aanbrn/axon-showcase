### Advisory — third-party inconsistency

**Vendored `axon4to5-migrate-code` — the `Discovery order` table omits the `serializer` recipe.**
(`.opencode/skills/axon4to5-migrate-code/SKILL.md:227-238`) The SKILL.md hard-coded discovery-order table lists eight
recipes (`aggregate`, `event-processor`, `command-gateway`, `query-gateway`, `query-handler`, `interceptors`, `saga`,
`event-store`), but the recipe catalog `references/recipes/` contains a ninth — `serializer` (its `RECIPE.md` declares
`order: 9`). The canonical auto-list `scripts/list-recipes.sh` iterates every non-underscore recipe directory and
therefore _does_ surface `serializer`; only the prose table omits it.

**Harm:** the project-mode recipe loop iterates "recipes in discovery order" per that table (`SKILL.md:123`), so a
`mode=project` migration — the exact use this repository vendored the skills for — would silently skip the serializer
recipe and leave AF4 `Serializer`/`axon.serializer.*` wiring un-migrated, contradicting the "Fully … compiling,
green-test codebase on AF5" goal.

**Decision:** report it upstream (AxonIQ/agent-skills, plugin `axoniq-migration` 0.2.2) with a reproduction, or
re-vendor at a newer upstream version that includes `serializer` in the discovery order. No local edit — this file is
vendored and out of fix scope. (Note: this is a vendored-file-internal inconsistency, not a "pattern our code
contradicts"; it is reported only because it would mislead the migration workflow the repo vendors the skill for.)

## Spec-corpus audit (`specs-auditor`)

**1 finding**

### Structural

**Imperative verb-phrase requirement headers where the corpus convention is a declarative noun phrase.** Seven
requirement headers across two specs are bare imperative verb phrases, while the corpus convention — stated in the
`agent-skills` spec that defines this audit (`showcase/quality/agent-skills/spec.md:133`, "a declarative header, a SHALL
body") — and followed by the other 20 specs is a declarative noun phrase. Each of the seven bodies is a SHALL statement,
so the headers read as the imperative form of the requirement rather than naming it. These are the only imperative
headers in the corpus; every other header is either a noun phrase or a declarative sentence.

- `openspec/specs/showcase/clients/web-ui/spec.md:11` `### Requirement: Browse showcases` → rename to
  `### Requirement: Showcase browsing`
- `openspec/specs/showcase/clients/web-ui/spec.md:27`
  `### Requirement: Reconcile the list with the eventually-consistent read model` → rename to
  `### Requirement: Read-model reconciliation of the showcase list`
- `openspec/specs/showcase/clients/web-ui/spec.md:63` `### Requirement: Drive lifecycle actions` → rename to
  `### Requirement: Lifecycle action dispatch`
- `openspec/specs/showcase/clients/web-ui/spec.md:84` `### Requirement: Validate the form before submission` → rename to
  `### Requirement: Create-form validation`
- `openspec/specs/showcase/clients/web-ui/spec.md:101` `### Requirement: Render a per-showcase history timeline` →
  rename to `### Requirement: Per-showcase history timeline`
- `openspec/specs/showcase/clients/web-ui/spec.md:112` `### Requirement: Display live events over SSE` → rename to
  `### Requirement: Live event display over SSE`
- `openspec/specs/showcase/gateway/live-events/spec.md:11` `### Requirement: Stream domain events over SSE` → rename to
  `### Requirement: Domain event streaming over SSE`

Because the header is a requirement's identity (a `MODIFIED` delta matches on it), renaming each header requires the
delete-and-add delta route, not an in-place `MODIFIED` retitle — fold this into the next change that touches either spec
rather than a standalone edit.
