## Spec-corpus audit (`specs-auditor`)

**2 findings**

### Stale

**1. The `dependency-management` spec omits `org.springframework` from its enumeration of major-disabled coordinates.**
`openspec/specs/showcase/quality/dependency-management/spec.md` (the "Major-disabled entries are limited to majors the
project cannot migrate" requirement plus the four coordinate-specific requirements) versus
`config/dependency-updates/major-disabled.properties:17`. The config lists `org.springframework` ("# Spring major
blocked: Spring Boot 4 migration deferred — see ADR-0004"), but the spec enumerates `org.jgroups`, `org.flywaydb`, the
three `org.opensearch.client:spring-data-opensearch*` coordinates, `org.springdoc:springdoc-openapi-starter-webflux-ui`,
and `org.axonframework` — with no requirement for `org.springframework` itself. The established pattern in this spec is
one requirement per suppressed group, each naming the coordinate and its rationale; Spring breaks that pattern.

**Suggested rewrite:** add a requirement
`### Requirement: Spring Framework major updates are suppressed until the Spring Boot 4 migration` (after the springdoc
requirement), with a body SHALL-including `org.springframework` as a group prefix, stating the rationale (Spring Boot 4
/ Spring Framework 7 deferred per ADR-0004), plus the standard "minor and patch updates stay visible" scenario —
mirroring the existing Flyway/springdoc requirement shape.

**2. The `gateway/rest-api` Purpose omits the CORS capability the spec now holds.**
`openspec/specs/showcase/gateway/rest-api/spec.md:5-7` (Purpose) versus
`### Requirement: CORS allows the standalone UI origin`. The Purpose describes the request/response contract (endpoints,
idempotency, cache fallback, error mapping) but never mentions cross-origin access, which the spec holds as a distinct,
fail-closed capability. The CORS requirement is a full capability (configurable allow-list, empty container default,
compose/bootRun local origins) added when the standalone web UI shipped; the Purpose was not refreshed to cover it. (A
terse Purpose deliberately scoping itself to the REST contract is defensible, so this is drift the Purpose-fit axis
targets rather than a hard defect.)

**Suggested rewrite:** extend the Purpose's closing clause to "…cache fallback on query failures, structured error
mapping, and configurable cross-origin access (CORS) for the standalone web UI."

### Advisory

**1. The query-service routes every controller method to the blocking scheduler — unrecorded band-aid (new).**
`showcase-query-service/src/main/java/showcase/query/ShowcaseQueryConfigurer.java:19-20` —
`configurer.setControllerMethodPredicate(__ -> true)`. This is byte-for-byte the same pattern as the gateway's
`ShowcaseBlockingExecutionConfigurer`, whose coarse routing is recorded as a parked band-aid in `docs/ideas.md:242-248`.
But the query-service's copy appears nowhere — not in `docs/ideas.md`, an ADR, a spec, or `AGENTS.md`. Its query path is
fully reactive (`ShowcaseQueryHandler` uses `ReactiveOpenSearchTemplate`, no `.block()`), so the all-methods-blocking
predicate is not self-evidently necessary. **Question:** why does the query-service mark every controller method
blocking — is it a legitimate necessity (some un-offloaded blocking call in the request-mapping path), or the same
coarse band-aid as the gateway's, and should it be parked/removed alongside it?
