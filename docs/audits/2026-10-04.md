**Suggested rewrite** of the redundant clause: "A proposal also passes a **promotion gate** before it is proposed — each
criterion, the gate's evidence threshold, and the source-verification rule are defined in the `agent-skills` spec and
`lesson-capture.md`. A rule that fails the gate is routed to a check, a spec, an ADR, or the change dir rather than the
always-loaded file." Trim the growth-bound clause to the applying agent's own instruction: "Applying a capture should
leave `AGENTS.md` no larger than it was; the applying agent records the applied net delta on the capture record
described above." (Ambiguous whether the inline one-sentence criteria summary is a deliberate quick reminder — a

### Advisory — third-party inconsistency

**The generated `opsx-sync` command + `openspec-sync-specs` skill invite a standalone "sync delta specs to main specs
without archiving" run, contradicting the load-bearing "Sync the main spec only at archive" rule
(`AGENTS.md:296-297`).** The excluded files instruct "Sync delta specs from an OpenSpec change to main specs… **without
archiving the change**", with trigger phrases (`"openspec sync"`, `"opsx sync"`) that invite a standalone run. **Harm:**
a standalone `/opsx-sync` writes the main spec to describe behavior the code has not been verified against, and
`openspec validate` cannot flag it — the exact silent drift the archive-only rule exists to prevent. The sync workflow's
legitimate use is inline within `openspec archive`. **Decision: change our usage** — document in the archive-only rule
that `/opsx-sync` is archive-internal and must not be run standalone. (Not an upstream bug — the command is default
OpenSpec behavior.)

## Spec-corpus audit (`specs-auditor`)

**2 findings**

### Stale

**1. `org.springframework` is suppressed in the shipped config but has no requirement in the `dependency-management`
spec.** `openspec/specs/showcase/quality/dependency-management/spec.md` (the suppressed-coordinate requirements)
enumerate `org.jgroups`, `org.flywaydb`, `org.opensearch.client:spring-data-opensearch` (+`-starter`/`-testcontainers`),
`org.springdoc:springdoc-openapi-starter-webflux-ui`, and `org.axonframework` — but
`config/dependency-updates/major-disabled.txt` also ships `org.springframework` ("Spring major blocked: Spring Boot 4
migration deferred — see ADR-0004"), which no requirement documents. The spec is the authoritative rationale record, so
Spring's suppression rationale lives only in the config comment.

**Suggested rewrite:** add a requirement (e.g.
`### Requirement: Spring major updates are suppressed until the Spring Boot 4 migration`) stating the config includes
`org.springframework` as a group prefix, with the rationale "Spring Boot 4 migration deferred — see ADR-0004", plus the
two standard scenarios ("Spring major jump is suppressed" / "Spring minor and patch updates stay visible"), mirroring
the Flyway/Axon group-prefix requirements.

### Duplicate

**2. The `dependencySecurityCheck` invocation is described differently in two specs.** `dependency-security/spec.md:60`
says "runs the Snyk dependency scan (`snyk test --all-sub-projects`)" (omitting the policy path), while
`merge-governance/spec.md:223` spells it "Snyk `test --all-sub-projects --policy-path=.snyk`". The task as declared
(`dependency-security-conventions.gradle.kts:11`) passes `--policy-path=.snyk`, so the owner spec under-names the
command the cross-referencing spec spells correctly. The flag is load-bearing — it is how the
`.snyk`-suppressed-findings scenario takes effect.

**Suggested rewrite:** in `dependency-security/spec.md:60` (and the "Developer runs the dependency security scan"
scenario), name the full invocation `snyk test --all-sub-projects --policy-path=.snyk`, so both specs describe the same
command.

## Architecture audit (`architecture-auditor`)

**1 finding, 2 advisory**

### Findings

**1. ADR-0003 mislabels the Elasticsearch Java client as "the OpenSearch Java client."**
`docs/adr/0003-retain-jackson-2-defer-jackson-3.md:16` — "the OpenSearch Java client
(`co.elastic.clients:elasticsearch-java`) already brings Jackson 3 artifacts…". `co.elastic.clients:elasticsearch-java`
is the **Elasticsearch** Java client; the OpenSearch client is `org.opensearch.client:opensearch-java` (the one ADR-0012
covers). The `Revisit when:` line on the same ADR names it correctly, so the Context is internally inconsistent with the
Decision it introduces.

**Suggested correction:** reword line 16 to "the Elasticsearch Java client (`co.elastic.clients:elasticsearch-java`)…".

### Advisory

**1. ADR-0003's deferred condition appears met — the Jackson-3 gate has shifted from "not yet" to "substantially met."**
`docs/adr/0003-retain-jackson-2-defer-jackson-3.md:7` — "Revisit when: the pinned `org.axonframework` and the
Elasticsearch Java client … resolve Jackson 3." Verified against the pins: `elasticsearch-client-java = "9.5.4"`
declares `tools.jackson.core:jackson-databind`/`jackson-core` as non-optional runtime dependencies, and
`axon-framework = "4.13.2"` now declares `tools.jackson.core:jackson-databind` as an optional dependency — Axon 4.13 has
gained Jackson-3 support since the ADR (2026-08-18) characterized it as "targets Jackson 2". The elasticsearch half was
already true at write time. **Question:** is the Jackson-3 backend migration now due for revisit, or does Axon's
Jackson-3 support being _optional_ (opt-in, not the default) mean the gate is still not met?

**2. The LZ4 relocation's rationale is unrecorded — the `.because()` string is tautological.** `build.gradle.kts:74-84`
—
`substitute(module("org.lz4:lz4-java")).using(module("at.yawk.lz4:lz4-java")).because("Force relocation of LZ4 implementation")`.
`AGENTS.md` records only the mechanism, and the `.because()` restates _what_ the substitution does, not _why_ the build
redirects to a third-party rehost (yawkat's `at.yawk.lz4` republish of `org.lz4` — a supply-chain-relevant swap).
**Question:** why is `lz4-java` force-relocated from `org.lz4` to `at.yawk.lz4`?

**Recorded, not reported:** the presence of `co.elastic.clients:elasticsearch-java` on the read side with no ADR
explaining why the read side depends on Elastic's client at all is already parked at `docs/ideas.md` (2026-10-03),
naming the same gap and the intended home (extend ADR-0012 or ADR-0003).
