# Load-test baseline: 2026-09-26

The first measurement from the reworked load tests (`scripts/load-test-baseline.sh`), recorded as the input for the
resource-sizing change. **Host-relative**: the load generator shares the host's CPU with the cluster, so these are
relative guidance, not absolute capacity.

## Target

- Local Helm cluster (`./gradlew helmInstallToLocal`), reached through the gateway ingress hostname
  `http://axon-showcase-api`.
- Node: **10 vCPU / ~16 GiB** (colima), carrying the app tier, PostgreSQL, Kafka, OpenSearch, and the kps/tempo
  observability stack.
- App tier: 5 pods (gateway 1, query 1, projection 1, command 2), chart default resources (1 CPU / 0.5–0.75 GiB
  requests, 3 CPU / 1–1.5 GiB limits).

## Method

1. **Calibrate** — `calibrate` ramp to 200 workload units/s over 5 minutes; a workload unit is a read iteration (the
   list fetch and a showcase fetch) or a completed write lifecycle.
2. **Knee** — the sustained rate where the response time departs the flat baseline, derived from the run's log by the
   `kneeFinder` task. **Not measured**: the 200-unit/s ramp never sustained a departure (p95 stayed ~8 ms), so the tool
   falls back to its ceiling (199 units/s) and flags it as unmeasured rather than reporting a knee.
3. **Baseline** — a 10-minute constant plateau at **119 units/s** (60 % of the calibration ceiling), read share 0.75, 10
   SSE connections held for the plateau, sampling `kubectl top pods -n axon-showcase` throughout. Raise `CALIBRATE_RATE`
   above 200 to reach a measured knee.

## Result

- Requests: **232,080** over the 10-minute plateau (**385 rps**), 0 failed.
- Response time: mean **5 ms**, p95 **8 ms**, p99 **11 ms**, max 442 ms.

Per-service CPU / memory during the steady-state plateau (`.25` CPU ≈ 250m):

| Service                    | CPU                           | Memory                 |
| -------------------------- | ----------------------------- | ---------------------- |
| api-gateway                | ~0.74–0.78 cores              | ~503 Mi                |
| command-service (2 pods)   | ~0.14–0.27 cores each         | ~473 / ~519 Mi         |
| query-service              | ~0.39–0.41 cores              | ~370 Mi                |
| projection-service         | ~0.065 cores                  | ~427 Mi                |
| web-ui                     | ~0.001 cores                  | ~44 Mi                 |
| postgres (db-events)       | ~0.22–0.27 cores              | ~0.71–0.87 GiB         |
| kafka                      | ~0.12–0.17 cores              | ~1.30–1.34 GiB         |
| opensearch (data / master) | ~0.15–0.17 / ~0.18–0.19 cores | ~1.54–1.57 / ~1.04 GiB |

The gateway is the busiest app pod at this operating point (~0.75 cores) — close to its 1-core request but well inside
its 3-core limit; the JVM services' 3-core limits are far above what this plateau needs.

## Caveats

- Point-in-time and host-relative: a different colima shape or a differently-loaded host changes these numbers.
- The generator runs on the host and competes for the same physical CPU as the cluster.
- SSE connections are counted separately from the request rate (they model browser tabs, not per-request load).
- No chart values were changed here — this baseline is the input to the separate resource-sizing change.
