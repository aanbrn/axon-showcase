## The finding (a recurrence, not a new one)

**The 2026-09-19 retrospective's central finding recurred and worsened.** That retro asked whether the consolidation
trigger could fire without a human. The trigger landed — the weekly `audit.yml` — and the accreted count is its control,
yet the file grew faster:

|                          | 2026-09-19 | 2026-09-28       |
| ------------------------ | ---------- | ---------------- |
| `AGENTS.md` lines        | 1,835      | **2,358** (+523) |
| top-level bullets        | 148        | 159              |
| `captured:` markers      | 34         | **89**           |
| auditor's accreted count | 24 → 16    | **87+**          |

**87 of 118 merged PRs touched `AGENTS.md` (~74%)**, and 50 titles are meta
(`Capture|Park|Record|Document|Apply|Widen`). The mechanism now _reports_ growth but never _shrinks_ it: the 2026-09-28
audit's own two findings (one merge, one removal — the duplicated `gh` grant and the duplicated `check`-task
enumeration) are **still unapplied in `AGENTS.md`** as of this retrospective, verified by grep. Applying them is an
owner-gated unit of its own, so between audits the file only grows.

## Lessons carried through this window

The window's captures are unusually thorough — the load-test, right-sizing, expiry, config-probe and dual-major lessons
are all recorded. The durable lessons **not** yet covered are about process rather than code:

1. **A judgment-shaped obligation loses to flow, and a second violation needs a mechanism, not more prose.** The capture
   subagent was skipped twice — after `scope-capture-trigger-to-the-unit` and after `check-unique-cron-schedules` —
   found only by the merge-time read, despite a "Do not skip the subagent" clause already in the capture bullet. The
   rule is unambiguous; what is missing is a way to _see_ the skip without re-reading a thread.
2. **The planning boundary is stated for the proposer, not for its delegations.** The propose workflow says to keep
   inspection read-only, yet a propose-stage delegation edited implementation files out of stage. No rule binds a
   delegated subagent, and the boundary is a property of the work, not of the agent performing it.
3. **A config consumed only by an out-of-repo runner is verified by dispatch and by nothing else.** The 2026-09-24
   OpenCode config migration left both cloud workflows **dead for five days** — no in-repo gate loads the config with
   the action's binary, and the failure was invisible until a manual `gh workflow run`. The window recorded the rule;
   the class has no mechanical check.
4. **A discipline that is stated but never measured does not hold.** "Applying a capture should leave `AGENTS.md` no
   larger" is in both the capture bullet and the spec, and the window still applied +55 markers and +523 lines. The
   capture's verdict reports additions and retirements but never their _size_, so the discipline is unfalsifiable at the
   moment it matters.

## Went well

- **The delivery discipline held end to end.** Nothing was committed before the owner's approval, and the review gate
  ran on every unit — docs captures and standalone fixes included. This is now the norm rather than an aspiration.
- **Premise interrogation caught two real drifts**: a proposed change pre-empting a parked idea about the same
  requirement, and a config that had silently made a tool major a repo prerequisite.
- **Dispatch-as-verification proved its worth**, surfacing a five-day outage no in-repo gate could see.
- **Two of the prior retrospective's named product candidates shipped** (#357, #362).
- **The new checks closed their loops in-window**: cron uniqueness and the conflict-marker/executable-bit checks landed
  with their specs, and the drift check shipped with the reference it reads.
- **The definition smoke-run paid again** — the one run for `scope-capture-trigger-to-the-unit` found two stale facts
  two merged units had left behind (#433). Second consecutive window where a smoke-run found real defects beyond its
  seed.

## Went wrong

- **The capture subagent was skipped twice**, each caught only at the merge-time read — a repeat of a recorded failure
  mode whose remedy is prose.
- **A propose-stage delegation edited implementation files out of stage** — a boundary breach no rule covers.
- **`incomplete-sweep` recurred across review rounds** (artifacts under-describing a change: delta → tasks → a doc's
  surface list), needing a _derive-by-grep_ root-cause fix rather than per-instance patching. Now covered by the
  window's own doc-consistency work, but it was the window's clearest review-loop cost.
- **The aggregation is charitably quiet about magnitude**: net +523 lines over nine days with 87/118 PRs touching the
  file, and the audit's accreted count at 87+.
- **The 2026-09-28 audit's merge/removal findings landed as a report, not as applied edits** — normal cadence, but the
  structural reason the file keeps growing.

## Improvement suggestions

| #   | Suggestion                                                                 | Class     | Disposition                                                                                                                                                                                                       |
| --- | -------------------------------------------------------------------------- | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| S1  | Make the per-unit capture a visible artifact, so a skip is a missing box   | `process` | Taken as `make-the-capture-visible` — the `AGENTS.md` capture bullet, the config `tasks` rule, the pull-request checklist, and the `agent-skills` scenario                                                        |
| S2  | Bind the planning boundary to delegations, not only to the proposing agent | `process` | Taken as `bind-planning-boundary-to-delegations` — the `AGENTS.md` OpenSpec Workflow Agreement                                                                                                                    |
| S3  | Add an in-repo read-path probe for `.opencode/opencode.json`               | `system`  | `docs/ideas.md` (parked) or a `commit-hygiene`/CI change                                                                                                                                                          |
| S4  | Make the capture's "no larger" discipline observable                       | `process` | Taken as `make-capture-growth-observable` — the `lesson-capture` growth paragraph and report contract, the `AGENTS.md` capture bullet, the config `tasks` rule, the PR checklist, and the `agent-skills` scenario |

**S1 — make the per-unit capture visible as an artifact.** The unit records a capture task or PR-checklist line that the
merge-time read verifies, so an unrun capture is a missing box rather than a recollection. Evidence: the subagent was
skipped after `scope-capture-trigger-to-the-unit` and after `check-unique-cron-schedules`, both caught only at the
merge-time read — session-sourced, with only the earlier skip recorded in `AGENTS.md`, and an identical skip was
recorded before this window.

**S2 — bind the planning boundary to delegations.** A delegation made at the propose/planning stage is read-only against
project code, the delegation prompt states the paths it may touch, and the calling agent verifies it stayed inside them.
Evidence: a propose-stage delegation edited implementation files out of stage (session account, single occurrence —
judge it against the two-occurrence threshold, leaning on the "clear preventive action" clause). The generated
`.opencode/commands/opsx-propose.md` cannot carry the fix, so the durable home is `AGENTS.md`, injectable also through
`openspec/config.yaml`'s per-artifact rules.

**S3 — probe the OpenCode config's own read path.** The `ci.yml` quality-gate step already probes the OpenSpec config's
read path (a probe change plus a warning grep); `.opencode/opencode.json` has no equivalent, so a v1-incompatible key
passes every gate and kills both cloud workflows until a dispatch. The probe should load the config with the same v1
line the action installs — probing the consumer's own read path rather than a second parser — or, if that is too heavy
for the PR gate, run weekly on the audit schedule and keep the dispatch rule. Evidence: both cloud workflows dead
2026-09-23 → 09-28; recorded in #438/#440; found only by `gh workflow run`.

**S4 — make the capture's "no larger" discipline observable.** Add to the capture verdict the _proposed_ net `AGENTS.md`
delta (additions minus retirements, in lines) and have the applying agent record the applied delta. Net growth then
stays a stated justification the merge-time read can see, rather than a post-hoc audit count. Evidence: +523 net lines,
+55 markers, 87 of 118 PRs touching the file while the "no larger" clause was already in force. The audit-side trend and
the carry-findings-forward items are already parked, so this covers only the capture-side delta.

**Not re-proposed, because the window already covers it:** the check-evidence family (#376/#377/#378/#380/#382/#437);
the dual-major config's prose rule (#434/#438/#440) — S3 adds only the mechanism; the load-test measurement lessons
(#418/#419/#420/#427/#428/#431); the scheduling and off-peak rules (#435/#436); the derive-by-grep sweep rule for
`incomplete-sweep` (#367's repeated-class flag); and the stale-record past-tense correction rule (#433).

## Recommended next direction

The tooling that reports the accretion now exists; the missing half is _application frequency_, and S1 and S4 are cheap
levers on it. But the window's strongest signal is that the process mistakes are the **unrecorded** ones — a skipped
capture, a delegation out of stage — because those leave no diff, and the capture gate itself is what was skipped. So
the highest-value next step is to make the capture a visible artifact (S1), and to let the second half of the window's
product momentum continue: the deployment smoke and the recorded load-test reference are new product-facing verification
surfaces that will need exercising on real merges.
