## The central finding (a recurrence, now structural)

**The previous retrospective's central finding — `AGENTS.md` grows faster than it shrinks — not only persisted; this
window made it structural: no merged PR shrank the file, and the one unit that applied an audit's de-duplication also
captured its own lessons, so the reduction was offset one-for-one.**

|                                   | 2026-09-28 | 2026-10-05        |
| --------------------------------- | ---------- | ----------------- |
| `AGENTS.md` lines                 | 2,358      | **2,693 (+335)**  |
| top-level (`- `) bullets          | 159        | 164 (+5)          |
| `captured:` markers               | 89         | **121 (+32)**     |
| PRs touching `AGENTS.md`          | 87 / 118   | **44 / 60 (73%)** |
| PRs with a **net-negative** delta | —          | **0**             |

Evidence:

- `git log 2535c11..HEAD -- AGENTS.md` is 45 commits; scanning every one for `insertions − deletions < 0` returns
  nothing — every `AGENTS.md`-touching commit this window was net-positive or flat.
- #446 (`Apply the 2026-09-28 audit's docs-route findings`) did apply both prior-audit findings — the duplicated `gh`
  grant paragraph folded, the CI `check` enumeration replaced with a cross-reference — yet its `AGENTS.md` delta is **+2
  lines** (28 insertions / 26 deletions) because the same unit also captured its two lessons. The de-duplication worked;
  it just did not net a reduction.
- The growth is _deepening, not widening_: +5 bullets but +32 markers — captures merge into existing bullets (the
  "prefer a merge or a replacement" discipline holds at the bullet level) while the prose around them lengthens.
- **The reduction half of the loop has no engine.** The 2026-10-04 audits' three-to-four reduction candidates are parked
  in `docs/ideas.md` (#502, dated 2026-10-05) to be "applied through that audit's workflow when next run" — but the
  scheduled `audit` workflow _reports_ (it opens a findings pull request); applying is a separate owner-gated unit. So
  candidates age while captures accumulate. The 2026-09-28 reductions landed only because a human opened #446 the next
  day.

**A second, sharper finding — the growth control the capture rule leans on is not a comparable metric.** The five
audit-report verdicts read **24, 16, 87+, 4, and ~71 accreted** (`docs/audits/2026-09-20.md`, `2026-09-21.md`,
`2026-09-28.md`, `2026-10-04.md`, `2026-10-04-scheduled.md`). These mix at least three definitions — markers (87+ ≈ 89),
distinct rule units (~71), and new-since-last-run (4) — so no trend can be derived. The parked idea "Trend the audit
counts across reports" is blocked by exactly this.

**A third — the window is the most meta yet.** No user-facing behavior shipped. The only product-facing artifacts are
the Grafana Web-UI panel (#480) and the GitHub-release capability (#490); the rest is audits, gates, tooling, and
housekeeping. The first retrospective's "make the next phase a product phase" (parked 2026-09-16) has now survived three
windows.

## Lessons carried through the window

The window's captures are thorough and mostly code- and verification-shaped, and they are already recorded in
`AGENTS.md`: the archive→spec-sync gotcha (`sync-audit-spec-findings-2026-10-04 (#497)`), the agent-loader frontmatter
lesson (`fix-readme-auditor-frontmatter (#477)`), the positive-control family (`scan-source-for-secrets`,
`validate-dashboard-json`, `declare-probes-with-shape-and-behavioural-checks`), the CLI-contract family
(`publish-github-releases`, `validate-the-workflows-on-ubuntu-2604`), and the containment and host-state family
(`pin-the-smoke-docker-to-overlay2`, `web-ui-coverage-gate`, `enforce-line-endings`).

The durable lessons the window did **not** cover, both about the audit/capture loop rather than about code:

1. **An applied de-duplication is not a net reduction when it rides its own capture.** #446 is the worked case: two
   removals plus two lesson captures net +2 lines. The rule "an implementation capture rides the unit's branch" is
   correct, but its consequence is that an audit-fix unit can never be net-negative. No rule states that consequence.
2. **A growth control that changes definition between reports is not a control.** The accreted count is the load-bearing
   number ("the control is the periodic `/audit-agents` pass — whose verdict already reports the accreted-rule count"),
   yet it is reported three ways. This is a spec-level report-contract gap, not a code bug.

  retrospective reported the same findings stranded. The mechanism can work.
- **The review and commit discipline held on every unit**, audit-fix and park units included; nothing was committed
  before approval.
- **The defensive checks landed with positive controls and specs** (secret scan, dashboard JSON, coverage, file sizes,

- **The lost-sync recovery was fast**: #496 (merge) → #497 (recovery) → #498 (capture) inside one morning, with the

- **The doctor's classification defect was found and fixed in a follow-up** (#460) instead of being shipped.

## Went wrong

- **A change merged with its archive move but without its spec sync (#496).** `openspec archive` wrote the delta→main
  sync, but only the change-dir move was staged; the merge shipped an archived change whose main-spec edits were absent,
  recovered as #497. The `openspec archive` gotcha had warned of exactly this hazard ("nothing is staged, so stage both
  sides") since 2026-09-15 — the prose rule existed and did not prevent it, and #498 recorded this as the first incident
  the gotcha now names.
- **The audit report filename collided**: the scheduled 2026-10-04 run reused the dispatch run's `docs/audits/<date>.md`
  and silently overwrote it (#494 vs #500), needing a rename to `2026-10-04-scheduled.md` to preserve both. Parked
  (#501) with a route; still a real loss.
- **Reduction candidates accumulate unapplied** — the 2026-10-04 audits' merge/route candidates are parked, so the
  file's growth bound has no scheduled engine.
- **Even the audit-application unit netted positive** (#446, +2), so the file has not shrunk in this window at all.

## Improvement suggestions

| #   | Suggestion                                                               | Class     | Disposition (proposed; none applied yet)                                                                                                        |
| --- | ------------------------------------------------------------------------ | --------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| S1  | Route the archive↔spec-sync hazard to a mechanical check                 | `system`  | An OpenSpec proposal on the `commit-hygiene` capability (code + test + spec delta); the `openspec archive` gotcha points at the new check       |
| S2  | Give the auditor's growth metric one definition                          | `process` | The `agents-auditor` definition + the `agent-skills` report contract (`MODIFIED` delta)                                                         |
| S3  | Give parked reduction candidates an application slot, not another report | `process` | The `/audit-agents` command + `agents-auditor` definition (the report PR carries the merge/removal edits), or a standing owner-gated apply unit |

**S1 — route the archive↔spec-sync hazard to a mechanical check.** The prose gotcha is recorded (#498), yet it did not
prevent the hazard it names. The pre-commit guard already inspects the staged set (`commit-hygiene.py --staged`); extend
it to pair an archive move with its staged spec sync: when a change dir under `openspec/changes/archive/**` is staged
and that change carries delta specs, fail if `openspec/specs/**` has unstaged modifications, allowing the no-delta /
`skip_specs` case by checking the archived change's own `specs/` dir. This is the promotion gate's "automatable at
reasonable cost → route to a check" case. If the `skip_specs` nuance makes it fiddly, park it in `docs/ideas.md` with
that caveat stated.

**S2 — give the auditor's growth metric one definition.** The "accreted count" is the control the capture rule names,
and five reports give 24/16/87+/4/~71 under at least three definitions. Fix one metric — recommend distinct rule units
carrying a `captured:` marker, reported as a total, with new-since-last-run reported separately. This unblocks the
parked "Trend the audit counts across reports" idea and is material because the file's growth bound is otherwise
unfalsifiable.

**S3 — give parked reduction candidates an application slot, not another report.** #446 proves application works; the
2026-10-04 candidates are parked to be "applied through that audit's workflow when next run", but the workflow reports
and never applies. Either the report PR could carry the merge/removal edits for the owner to review once, rather than
routing them to `docs/ideas.md`, or a standing owner-gated "apply parked reductions" unit could run per audit. This
refines — rather than duplicates — the parked "Carry findings forward across audit reports" idea, which addresses
reporting only. Because applying is editorial, this stays process, not a check.

**Already parked — not re-proposed:** the audit report filename collision (#501, routed to `audit.yml` and the
`merge-governance` spec); the weekly-report guarantee against dropped schedules (parked 2026-10-05); the LZ4 rationale
(#502); the ADR-0003 Jackson-3 revisit trigger and the Elasticsearch-client rationale (architecture audit); and the
`opsx-sync` archive-internal wording. The window's code-shaped lessons are all captured; no re-capture is proposed.

## Recommended next direction

The observability half of the growth discipline landed (S4) and the reduction cycle _can_ close (#446), so the missing
piece is making reduction a scheduled application with a comparable metric (S2 + S3), plus the mechanical safety net for
the one recurring merge hazard (S1). But the window's strongest signal is elsewhere: **three retrospectives have now
recommended a product phase and the window shipped none.** The tooling is mature — the four auditors, the toolchain
doctor, the gates, the deployment smoke, and the release workflow all exist. The next window's highest-value work is to
_use_ it: pick one of the parked product ideas and ship behavior a person can see, letting the audit loop run on its
reduced cadence rather than being the window's subject.
