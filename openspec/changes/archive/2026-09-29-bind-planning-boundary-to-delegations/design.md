# Design

## Context

See `proposal.md` — Why. The planning stage is read-only for the agent itself — the generated propose guidance says
"Keep inspection read-only" (`.opencode/commands/opsx-propose.md`) and explore mode "must NEVER write code or implement
features" (`opsx-explore`) — but neither binds a delegation the proposing agent makes, and the generated files are
rewritten by `openspec update`, so they cannot carry the fix. The incident (a planning-stage delegation editing
implementation files out of stage) is session-accounted, single-occurrence, and its delegate class was not recorded, so
the rule is written as a preventive boundary across all planning-stage delegations rather than for one delegate.

## Goals / Non-Goals

**Goals:**

- Bind the planning stage's read-only boundary to delegations: a path-scoped delegation prompt and caller verification
  before the delegate's output is used.

**Non-Goals:**

- Regulating implementation-stage delegations, which their change's tasks and the review gate already govern.
- A mechanical gate — no check can see a delegation prompt or an edit's stage.

## Decisions

### Decision: the rule lives in `AGENTS.md`'s OpenSpec Workflow Agreement

The section already owns the planning-boundary agreements (create the branch at propose; leave work uncommitted), and
`AGENTS.md` is loaded on every invocation, so it reaches the proposing agent at whichever moment a delegation is made.

- **Alternative — an `openspec/config.yaml` per-artifact rule (as `inject-positive-control-task-rule` did):** reaches
  the agent only when an artifact is created and would need repeating for `proposal`, `design`, and `tasks`, while
  `AGENTS.md` is loaded anyway.
- **Alternative — a clause in the review-gate bullet (the other home S2's disposition names):** that bullet governs the
  review pass, not delegation discipline, and would leave the boundary unstated until review time.
- **Alternative — edit the generated `opsx-propose` command:** it is regenerated by `openspec update`, so the fix would
  not survive.

### Decision: scope the rule to the planning stage, with the change artifact as its writable exception

The trigger is the planning stage — exploring a change or drafting its artifacts, before implementation — because
explore mode carries the same delegation gap (its no-implement rule binds the acting agent, not its delegates). The
delegate may still write the change's own artifacts under `openspec/changes/<change>/`, which drafting a plan requires;
everything else in the project is read-only.

- **Alternative — bind every delegation:** over-broad, and false for a work delegation that legitimately edits code
  under its change's tasks.
- **Alternative — the propose stage only:** leaves the identical explore-stage gap open.

### Decision: no spec delta (`skip_specs`)

The boundary is agent process control flow; no capability covers planning-stage delegation discipline, and a requirement
invented to satisfy validation would describe nothing the system does. The spec corpus's `delegat` hits delegate content
to a target spec or ADR (`agent-skills`), visual review to the `vision` subagent (`agent-skills`), and presence
validation to complementary constraints (`identifier-extension`) — none covers a caller/delegate read-only boundary or
the planning stage.

- **Alternative — add a scenario to `agent-skills`:** the capability describes subagent behaviour, not the main agent's
  delegation discipline.

### Decision: apply the suggestion on owner adoption, not on the promotion gate

The incident is session-accounted and single-occurrence, so this addition does **not** independently meet the promotion
gate's "one severe **verified** incident" threshold — the incident cannot be verified against the repository. It is
applied because the owner adopted retrospective suggestion S2, whose preventive action is clear and whose cost asymmetry
(a cheap rule against a contaminated plan) justifies it. Recorded explicitly rather than presented as a gate pass;
parking it in `docs/ideas.md` until a second occurrence is the alternative if the owner judges the evidence too thin.

## Risks / Trade-offs

- **A session-sourced, unverifiable incident** → the rule states a behaviour (read-only + verify), not a factual
  history, so it stands on its preventive value; the incident is labelled session-accounted rather than asserted as repo
  history, and the gate admission above states the shortfall.
- **`AGENTS.md` growth** → one paragraph; the capture's "no larger" discipline applies and is the subject of S4.
