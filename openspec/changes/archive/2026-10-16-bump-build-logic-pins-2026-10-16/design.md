# Design

## Context

See `proposal.md` — Why. The five were **re-resolved** with the repo's own check rather than read off the tracker issue:
`./gradlew buildLogicUpdates` reports them at their current releases, so nothing has moved since the issue refreshed —
the re-resolve is the step, as the update-check rule records.

What the five are, and what each one's bump can reach:

- `lombok-plugin` (`9.5.0`→`9.8.2`, a minor) drives compile-time codegen, so its effect is in the compiled classes and
  the integration tier is the one that exercises it.
- `errorprone-plugin` (`5.1.0`→`5.1.1`) and `spotbugs-plugin` (`6.5.10`→`6.5.13`) are patches to the static-analysis
  gates; an incompatibility fails the build rather than a test.
- `gatling-plugin` (`3.15.1.2`→`3.16.0`, a minor) is the load-tests module's plugin — its sources and tests compile in
  `check`; the simulations themselves are opt-in.
- `dependencyVersions-plugin` (`0.61.0`→`0.66.0`) is the update report's own plugin.

Two documents name a bumped version, and the two readings differ:

- `docs/ideas.md`'s parked Gatling note said "gatling-gradle-plugin 3.15.1.2" in a present-tense claim about the
  plugin's task. That is a live doc quoting the pin, which the docs-refresh rule covers: the note now names the pinned
  plugin rather than the number, so the same claim survives future bumps.
- `docs/adr/0007-…`'s Context names `io.github.ben-manes.versions` `0.61.0` as **the tool version the observation was
  made with**, not as the catalog's current value — a historical record of what ran. It stays as recorded, since
  rewriting it to the new pin would falsify the observation it describes.

The Snyk policy carries eight version-pinned coordinates across seventeen blocks, counted from the pre-change file
(`git show HEAD:.snyk`): seven Spring coordinates (`org.springframework:*@6.2.19`,
`org.springframework.security:*@6.5.11`) and one `com.tdunning:t-digest@3.3`, which two blocks carry. No bumped plugin
carries a Spring coordinate. **The Gatling bump kills the t-digest one**: `io.gatling:gatling-charts` `3.16.0` drops
t-digest and pulls `org.elasticsearch:elasticsearch-tdigest` instead (verified against
`:load-tests:dependencies --configuration gatlingRuntimeClasspath`, which no longer shows `com.tdunning`). The policy
has no staleness guard, so the two dead blocks are removed here rather than left to match nothing forever — leaving
seven coordinates and fifteen blocks.

## Goals / Non-Goals

**Goals:**

- Take the five pinned plugin pins the check reports as behind, at the versions the check resolves now.
- Leave every live doc that names one of them accurate under the bump.

**Non-Goals:**

- The tracker issue's other actionable rows — the catalog set (`caffeine` `3.3.0`→`3.3.1`, `grpc-bom` `1.84.2`→`1.85.0`,
  `swagger-ui` `5.33.1`→`5.33.2`) and the web UI npm rows. This unit is the pins the new check surfaced; those are the
  routine set's own unit.
- The pins a suppression defers (Spring Boot's `4.1.1`, Kotlin's `2.5.0-Beta1` are a deferred major and a pre-release
  respectively), which the check already filters and which need coordinated migrations.

## Decisions

**Take the five together, in one bump.** They share a surface (the included build's buildscript classpath), a
verification (`check`), and a rollout (the next weekly run's report). Splitting them per plugin would pay the full
verification five times for one change's worth of risk.

**Verify with the full `check` (integration tests included).** Lombok's minor bump changes generated bytecode, which
compilation alone does not exercise; the integration tier is what the Test-tiers convention puts a runtime-path or
codegen-affecting bump behind. The static-analysis bumps are self-verifying — a rejected plugin version fails the build.

**Fix the idea's quote by naming the plugin, not by updating the number.** A number in a parked note goes stale on the
next bump; the coordinate and the reason for the pin do not. This is the pattern the repo already uses where a version
would rot ("name the coordinate and the mechanism, not the constraint's version").

## Risks / Trade-offs

- **Lombok's minor bump meets a newer javac** → this is a known upstream compatibility axis, and the full `check`
  (compilation of every module plus the integration tier) is the mitigation.
- **The Gatling minor bump changes the load-tests module's plugin** → `check` compiles its sources and runs its tests; a
  simulation run stays opt-in and is not part of this unit's gate.
- **A static-analysis patch changes a rule's findings** → the gates run in `check`; a new finding would fail it rather
  than pass silently.

## Migration Plan

None: a version bump, taking effect on the next build.
