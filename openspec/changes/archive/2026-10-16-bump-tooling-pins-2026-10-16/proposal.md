# Proposal

## Why

The `toolingUpdates` report names two rows: `openspec-cli: 1.14.1 -> 1.14.2` and `snyk-cli: v1.1308.0 -> v1.1308.1`.
Both were re-resolved against each tool's own lookup rather than read off the tracker issue —
`npm view @fission-ai/openspec version` and `gh api repos/snyk/cli/releases/latest` — and both still point at those
versions, so the findings are current. The OpenSpec pin is the CLI that generates this repo's `opsx-*` commands and
`openspec-*` skills and that the `build` gate validates the spec corpus with; the Snyk pin is the CLI the credentialed
weekly scan installs.

## What Changes

- **`.github/workflows/ci.yml`, `opencode.yml` and `audit.yml`** — the OpenSpec pin `1.14.1` → `1.14.2` in each
  workflow's install step.
- **`build.gradle.kts`** — the `toolingUpdates` check gains the two entries the repo's own rule requires for a pin in
  more than one file. It read the pin from `ci.yml` alone, so `opencode.yml`'s and `audit.yml`'s copies were silently
  unchecked — the class the check's own guidance records. Each new entry is named per file (`openspec-cli (ci.yml)`,
  `… (opencode.yml)`, `… (audit.yml)`) and its file is registered in the check's `pinFiles`.
- **`AGENTS.md` and `docs/ideas.md`** — both named the pinned CLI as `1.14.1`. Per the repo's rule for a version a doc
  quotes, each now names the mechanism rather than the version — that no released CLI has `inspectProjectConfig`, and
  that `#1894` is still open — so neither rots on the next bump; the parked idea's version-pinned re-check threshold
  only restated the condition its own sentence states, and is deleted rather than renumbered.
- **`.opencode/commands/opsx-explore.md`, `opsx-update.md`, and six `.opencode/skills/openspec-*/SKILL.md` files** — the
  regeneration `openspec update` produces for the new CLI. Eight files change, all of them modifications rather than
  additions or removals, so the generated command and skill inventory is unchanged — no inventory-driven
  `AGENTS.md`/README edit. Four of the six skills change only their generated-frontmatter stamp; the two commands and
  the other two skills carry template changes. The two docs that named the pinned version are swept in the bullet above.
- **`.github/workflows/dependency-security.yml`** — `snyk-version` `v1.1308.0` → `v1.1308.1` in the `snyk/actions/setup`
  step. The action ref itself (`snyk/actions/setup@master`) is a deliberate floating ref Dependabot does not manage, and
  stays.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

None: a tooling-pin bump, which no capability spec covers (`skip_specs`). The specs that mention these files — the
agent-skills spec's generated-file exclusions and the code-quality spec's markdown scope — state that the generated
files are excluded from a formatter, not what they contain.

## Impact

- **CI**: the `build` gate installs the pinned CLI and validates the spec corpus with it, so the PR gate is the OpenSpec
  pin's own end-to-end verification; the local instruction files are generated by the same version.
- **The credentialed scan**: the Snyk CLI's pin can only be verified by a run that installs it, so this change
  dispatches `dependency-security.yml` from its branch before the archive.
- **No behavior change in the repository's own tooling**: the regenerated files are generated artifacts, and the pins
  are the CLI versions CI and the weekly scan install.
