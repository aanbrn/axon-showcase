# Proposal

## Why

The new `buildLogicUpdates` check's first run reported five pins of the included `build-logic` build behind, which the
main report cannot see: `dependencyVersions-plugin` `0.61.0`, `errorprone-plugin` `5.1.0`, `gatling-plugin` `3.15.1.2`,
`lombok-plugin` `9.5.0`, and `spotbugs-plugin` `6.5.10`. Re-resolved with the check's own lookup rather than read off
the tracker issue, all five are still current releases, so the finding is fresh. Taking them is what keeps the pinned
plugin set current — the gap the previous change closed was measured by `helm-plugin` sitting three scheduled runs
behind.

## What Changes

- **`gradle/libs.versions.toml`** — five bumps: `dependencyVersions-plugin` `0.61.0`→`0.66.0`, `errorprone-plugin`
  `5.1.0`→`5.1.1`, `gatling-plugin` `3.15.1.2`→`3.16.0`, `lombok-plugin` `9.5.0`→`9.8.2`, `spotbugs-plugin`
  `6.5.10`→`6.5.13`.
- **`docs/ideas.md`** — the parked Gatling configuration-cache idea quoted the pin as `gatling-gradle-plugin 3.15.1.2`;
  it now names the pinned plugin rather than the number, so the note survives the bump instead of going stale with it.
- **`.snyk`** — the Gatling bump moves `gatling-charts` off `com.tdunning:t-digest` (it now pulls
  `org.elasticsearch:elasticsearch-tdigest`), so the two blocks pinned to `t-digest@3.3` are dead; the policy has no
  staleness guard, so they are removed here, in the change that moves past them.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

None: a pure dependency bump, which no capability spec covers (`skip_specs`). The pins are not behavior — the
`dependency-management` spec states the reporting rules, not the versions.

## Impact

- **Build**: build plugins only — `errorprone` and `spotbugs` are the static-analysis gates (an incompatibility fails
  the build rather than a test), `lombok` runs at compile time (its generated bytecode is what the integration tier
  exercises), `gatling` is the load tests' plugin, and the versions plugin is the update report itself. No runtime-path
  library moves, so no service's behavior changes.
- **No source reflow**: the Spotless pin is not among the five, so no formatter changes and `spotlessApply` has nothing
  to reflow.
- **Observable**: the five rows disappear from the "Dependency updates" issue's build-logic pins section on its next
  run.
- **Security policy**: `.snyk` loses two blocks that no longer suppress anything. Removing a dead ignore is fail-loud,
  not silent: were the coordinate still resolved, the next credentialed scan would surface the finding instead of a
  stale ignore hiding nothing.
