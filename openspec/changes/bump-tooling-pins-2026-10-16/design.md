# Design

## Context

See `proposal.md` — Why. Both pins were re-resolved on 2026-10-16 against their own lookups, per the stale-target rule:
the OpenSpec CLI's latest on npm is `1.14.2`, and `snyk/cli`'s latest release is `v1.1308.1`. Neither had moved since
the report ran.

What each pin reaches:

- The OpenSpec pin is declared in **three** workflows — `ci.yml` (the `build` gate), `opencode.yml` and `audit.yml` (the
  unattended agent runs that must resolve the package) — while `toolingUpdates` reads it from `ci.yml` alone. The
  `/opsx-tool-update` command's stated job includes keeping the other two current for exactly this reason.
- The Snyk pin is the CLI the credentialed `dependency-security.yml` scan installs; nothing else reads it.

The regeneration is a second, consequential effect of the OpenSpec bump; what it changed is stated once in
`proposal.md`'s What Changes.

## Goals / Non-Goals

**Goals:**

- Take both pins the report names, at the versions each tool resolves now.
- Bring the two workflows the check cannot see into line with the pin, and regenerate the instruction files the new CLI
  produces.

**Non-Goals:**

- The Helm and Paketo findings, which are separate units (each needs an environment-specific verification).
- The `pack` and gitleaks pins: the report lists neither, so they are current.

## Decisions

**Take both pins in one unit.** They share the report, the trigger, and the verification shape (a re-run of the check
that produced them), and the repo's precedent treats the tooling findings as one unit.

**Verify the pins where each actually runs, not by a local replay.** The OpenSpec pin is verified by the PR's own
`build` gate, which installs it and runs `openspec validate --all` with it — and the local instruction files were
generated by that same version through `npx`, so the generated artifacts and CI agree. The Snyk pin cannot be verified
locally at all (its first real execution is the credentialed scan), so its verification is a dispatch of
`dependency-security.yml` from this branch before the archive commit, as the update-check rule requires for a
verification the local environment cannot run.

**Run the regeneration through `npx @fission-ai/openspec@1.14.2` rather than a global install.** A global
`npm install --global` failed with an `EEXIST` on the bin link, and what the step needs is the version the templates
come from, not where the package lives.

## Risks / Trade-offs

- **A pin's tag may not install** → the dispatch (Snyk) and the PR gate (OpenSpec) are the runs that install it; a red
  run attributed to the install is the pin, and one attributed to a finding is the policy.
- **A newer CLI may parse `config.yaml` differently** → the command's own probe verifies it: a healthy config reads its
  declared lists with no warning, and each warning pattern fires when exercised, so a silent pass is not vacuous.

## Migration Plan

None: pin updates and regenerated artifacts, taking effect on the next CI run.
